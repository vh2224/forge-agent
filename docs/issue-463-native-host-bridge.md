# Issue 463: owner-bound native host bridge

This document defines the owner-bound native bridge protocol and its verification boundaries. Implementation, providerless tests, controlled host observations, actual same-session execution, CI and installation are separate evidence. The supported profile is a bounded contract; a private diagnostic or an IPC control alone does not prove an operational Forge unit or human acceptance. Test and delivery results belong in the corresponding reports and release evidence.

## Original workflow and current authority

The normal loop already sends its real workflow through `options.workflow` to orchestration. An ordinary `beginSerial` can record its immutable workflow projection in the original BEGIN, together with the actual unit, slice, milestone, host, owner digest and acquired lease generation. The `unit-began` event carries the binding digest. Existing transaction checksums, event proofs and physical positions remain required.

`remaining_steps` and other changing loop counters are not identity. A replay of the same workflow preserves the binding and event bytes; another workflow cannot replace them. The stored binding is correlation and integrity evidence, not current authority or a signature. Native preparation independently rechecks the real actor, run, held claim, lease, BEGIN, physical roots, gates, inputs and questions.

The bridge prepares after BEGIN. It does not create or advance a workflow, select a unit or begin another task. CLI workflow and dispatch values are selectors only. A legacy BEGIN without this binding remains valid for its existing lifecycle, while the new bridge refuses `native-host-workflow-binding-unavailable`. No history is backfilled or rewritten. Present malformed bindings do not receive legacy treatment.

Workflow identity is preserved byte-for-byte from the real producer; it is not an ASCII Task/Milestone ID or silently normalized to NFC. The current question API supports a narrower workflow vocabulary. A workflow outside that vocabulary can persist/replay generically, but bridge preparation refuses `native-host-workflow-question-scope-unsupported`. The candidate does not widen the question helper or query a different normalized identity.

## Request construction

`buildOwnerContext` reads the already-created canonical BEGIN. It builds the internal `inspectAttempt` used by `validatePending` from the exact persisted workflow and canonical question state/origins. Workflow-only pending questions block even if the CLI omits its workflow selector. Milestone, unit and planning questions are also checked. An unrelated foreign workflow does not cause an owner-wide refusal.

`buildExecutionRequest(context, ownedChannel)` returns an opaque process-local request handle. The Bridge owns the genuine channel and its physical external custody/admission. Request readers return copies; JSON cannot reconstruct the handle. The builder produces the canonical rendered prompt, a bounded complete context file through channel admission, current route/model/effort, exact plan and optional research/security inputs, claim/roots, resolved budgets, verification commands and constraints. Deployment is unsupported. Required context and procedure modules are preserved; optional standards use their current resolved allowance.

Explicit `verification_bindings` in the closed owner input are coverage declarations, not approval or evidence. The constructor freezes those declarations in the genuine context/request and validates their criterion selectors, aspects, roots and source checks against the actual plan and normalized verification command seal. Missing declarations refuse; the constructor never maps every truth to the first check or imports a test declaration helper.

An approved plan file remains supported. The actual `plan_gate.interactive: off` preference permits the canonical `interactive-off` decision in auto, task and step modes, before considering unavailable auto-defer producers. Auto defer under an enabled interactive policy still requires its genuine opaque owner producer and currently refuses `native-host-auto-plan-gate-producer-unavailable`; missing `auto` findings likewise has a named refusal. No approval receipt is fabricated. Security readiness means the canonical scan plus actual checklist structure, including the canonical em-dash header, not that unchecked risks have already been resolved. Not-applicable security uses no dummy file; native execution/delivery packaging must consistently omit it.

## Profile, original invocation and join

Capability and activity admission happen before ToolUse or Agent instance IDs exist. Sealing happens inside the original native callback. The native execution module must mint a WeakMap witness for its exact request, arguments and invocation. The profile verifies that witness and the callback data against the complete effective invocation. A selfhash or a matching plain object cannot seal a request.

Native identities use the producer's `forge-code-roots.digest` over the original object insertion order. The new profile wire/schema digest is a separate sorted protocol hash. Shape validation does not reorder callback objects before comparing native identities.

Current profile checks reobserve the Agent source, schema/configuration, host/relay/session and owner facts. Candidate input is separate from captured host output. Raw captures are retained before parsing or refusal; the actual result-envelope parser and result contract must agree with the candidate payload. The callback and the supervision subscription share the same joined-return barrier. Neither may return a valid terminal result before the foreground return and all known native writers are reconciled.

Retained raw bytes and every returned snapshot use independent unpooled buffers. Join rehashes and reparses retained bytes instead of relying only on an old parsed object. A caller can mutate its returned backing ArrayBuffer without acquiring the retained capture. The coordinated genuine-profile fixture must exercise this backing-alias boundary; a passing data-only parser test does not establish it.

After real publication, `assertPublicationCurrent(profile, witness)` accepts only the original process-local publication witness produced by NativeDelivery and validated by NativeExecution, including exact manifest/receipt/artifact readback. Request assertions may receive that same opaque witness in internal options. The original context snapshot binds every artifact preimage. Only a previously measured context source whose before/after bytes match that witness may retain its original logical context identity; every current readback is checked again. Task PLAN, questions, actor, run, claim, lease, roots, gates, routing and host sources still undergo normal current validation. JSON clones, another witness, unmeasured preimages and unrelated drift refuse. Native's witness validator must not call Request/Profile/Activity, avoiding a validation cycle.

The separate `forge-native463-fixture-foreground-v1` derivation retains its fresh marked physical temporary root, contained owner/code/channel/private homes, explicit writer records and candidate/capture equality. It always reports provider evidence as `unknown`. It is not an observed Claude profile or real-provider E2E. JSON `joined`, `terminal`, `provider_called`, approval flags or provenance labels cannot substitute for genuine process-local witnesses and measured origin.

The new `claude-agent-files-foreground-v1` candidate supports a narrow Windows profile with the locally measured Claude 2.1.322 binary SHA256 `345996b4bdbae21d817f750fae2f34cbf8d81224a5444c78136091d121beb298`. This catalog binding is not proof that a host ran, consumed its Agent definition, or joined. The profile uses the distinct `forge-native-files` Agent with Read/Write only, explicit routed model/effort and foreground constraints; owner-side canonical code performs verification and publication. Generic executors, preferences and tool sets are unchanged. Unknown binaries, ambiguous Agent/config sources, disabled or unsupported hook settings and unknown host shapes refuse. The older generic unmeasured profile still refuses rather than gaining authority from a JSON observation.

Before Tool IDs exist, enrollment yields only supported invocation intent and sealed argument data. A genuine original PreToolUse hook in the same session/window must match those arguments before execution admission. The physical installed Hook is resolved from the canonical Claude runtime home (including CLAUDE_CONFIG_DIR), separately from Core/scripts. Current actor, OS process/source/argv, unique Agent definition and fixed wildcard fail-closed hook settings are reobserved. Original prepare handoff also requires the actual closed Bash command body before window creation; an unknown wrapper, interpreter, suffix or unobservable shell refuses `native-host-prepare-shell-wrapper-unsupported` instead of being adopted. A controlled Bash-only observation of the pinned Claude binary captured three nested Git Bash `-c` processes with the same complete wrapper body and the exact admitted command in its `eval` payload. Support requires the complete observed wrapper grammar and bounded contemporaneous validation of every referenced snapshot; a missing or unsupported snapshot is not trusted by path or by an old hash. The original diagnostic did not retain that snapshot, and its result alone cannot authorize the wrapper. This is separate from a real Forge unit or the original interactive session.

The supported return subset requires the correlated Agent IDs, actual completed PostToolUse response, dynamic Read/Write ledger, unique toolsUsed set, consistent operation counts/toolStats and zero known worker tasks pending. SubagentStop alone is not join. Actual usage may establish provider evidence; model labels, clock/PID, Stop and success flags do not. Service-applied effort remains unknown. The profile does not pretend to have a complete published Agent JSON schema. Unknown fields or incomplete evidence refuse.

The cooperative relay uses a fresh per-attempt 256-bit HMAC key, private ACL before key creation outside Owner/Codes, current original signer checks and replay-resistant session/window/request/dispatch bindings. Locators, paths, roles and nonces alone are not authority. This is not kernel peer authentication, an OS sandbox or a defense against arbitrary same-account processes. Private IPC positive/negative controls are separate evidence; the broad-ACL physical negative could not be exercised because Windows refused creating that dummy ACL. None of those controls validates the LIVE host pipeline.

## CLI handoff and acceptance

Resolve the Node executable, current Core scripts and input file to physical absolute paths before opening the window. Create the closed selector/verification input in a separate already-completed operation. Preparation does not accept an approval flag or arbitrary callback, create another BEGIN, or choose a different unit. Invoke one literal Bash command, substituting all three observed absolute values before the call:

```text
"<NODE_EXECUTABLE_ABS>" "<FORGE_SCRIPTS_DIR_ABS>/forge-native-host-bridge.js" prepare --input "<NATIVE_HOST_INPUT_ABS>"
```

No shell assignment, prefix/suffix, variable expansion, pipe, redirection or hidden script is allowed. The normal LIVE path omits `--host-observation`; that option belongs to the explicitly isolated fixture path. The original prepare Node/factory/context/input and actual shell body are measured before the window. The single initial completed PostBash must carry the exact original prepared JSON stdout and authenticated tool_use_id. The controlled observation omitted the one terminal LF emitted by Node; only that demonstrated omission is accepted, without trimming or reparsing arbitrary caller text. The optional observed `noOutputExpected` field must be a boolean. Interrupted, failed, missing, truncated or another attempt's output cannot complete handoff. Do not reconstruct arguments or discard context to repair truncation. Handoff is not Agent join.

The host reads the full pending-host prepared JSON and invokes the exact sealed Agent arguments in the same session. After the genuine correlated return is retained, run `control_commands.accept` verbatim. The LIVE command is `accept --attempt ABS`, without a parent-written candidate file; it selects only the original retained capture. Explicit candidate files remain fixture/compatibility data and cannot mint captured output or join.

An accepted/retained command or exit0 is not ready. Accept returns retention promptly so its real PostBash can close the known-writer barrier. That authenticated Post then waits for canonical verification, publication, exact original-witness readback and completed Activity settlement before returning the ready ACK. The owner remains warm until the authenticated receiver confirms the ACK. A cut after Post admission does not fabricate failure or ready: the same live owner can finish its canonical work, and authenticated read-only status can recover the ACK using the retained original publication witness, current actor/session/source checks, exact manifest/receipt/artifact readback and `assertSettled`. It does not reopen a window or acquire authority from checkpoint JSON. Only the additional IPC idle deadline is disarmed during an authenticated completion-pending response; canonical verification budgets and hook limits remain in force, without synthetic progress.

Historical status after actual owner loss remains read-only and does not reconstruct authority or prove join. Warm replay uses the retained original owner/session/receipt and returned replay command; LIVE replay begins only after its genuine PostBash barrier, without new inference, BEGIN, run/start or a fabricated published result. Missing original authority remains a named refusal.

## Verification boundaries

The integration includes original-callback and original ready/publication witness producers, Bridge/profile consumers and Activity/supervision. Their existence and static review are not execution evidence; they must be exercised together under the declared physical roots and authority. Selected spool and atomic-staging writers require prewrite admission; a postwrite `persistDeliveryReceipt` notification is not admission. Canonical owner publication retains its original guard/CAS/readback boundary. Unsupported staging paths refuse. Transport caps do not replace model budgets.

Original ready receipts remain publication-pending until real materialization/readback and activity settlement. Fresh replay uses the original session's `replayReady` record and explicit artifact readback; it does not call `run` or `start`, invent a recovery reservation or synthesize `published: true`.

Request tests use genuine private run/claim/lease/BEGIN authority; the providerless CLI fixture covers the complete request, original callback, prepared stdout bytes versus the original immutable checkpoint before Agent launch, terminal-before-join, verification/publication and original replay. Synthetic data negatives cover failed/interrupted/truncated/foreign prepared output without creating a fake genuine proof. Actual same-session Claude hook/OS ancestry and Bash schema, explicit arguments/current definition, file boundaries, captured acceptance, joins, readiness/owner-close behavior and replay must still be measured before any operational-success claim. Existing fixture bytes, Source manifests, registry counts and successor projections remain independent preservation gates.
